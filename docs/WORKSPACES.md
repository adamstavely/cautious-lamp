# Workspaces and applications

A workspace is a team's space: its members, its items (fonts, tokens, guidelines and 15 other kinds), the components and applications that belong to it, and what it shares with other workspaces. Applications are the products that use the design system; each can belong to a workspace.

Both are stored in Elasticsearch and every route needs a signed-in principal (see [AUTH.md](AUTH.md)). Identity comes only from the principal: requests can't name a user, owner, `addedBy`, `createdBy` or "requesting workspace". Bodies with unknown fields are rejected with `400`.

Code: `backend/src/workspaces/` and `backend/src/applications/`. Frontend: `WorkspaceManagement.vue`, `WorkspaceDetail.vue`, `ApplicationManagement.vue`, `ApplicationRegistration.vue`, `components/workspaces/`, `components/applications/` and `composables/useWorkspaceResource.js`.

## Roles

Each member has one role in a workspace:

| Role | Can |
| --- | --- |
| `viewer` | Read the workspace, its members, items, components, applications and analytics |
| `editor` | Also add, change, delete and share the workspace's items (and share its components) |
| `admin` | Also change settings, add and remove editors and viewers, change their roles, make items global, register and change the workspace's applications |
| `owner` | Also add, promote, demote and remove admins, transfer ownership and delete the workspace |

- A workspace has exactly one owner: whoever created it, or the user named by an `admin:users` holder in `ownerEmail`. Ownership only moves with `POST /workspaces/:id/transfer-ownership`, to an existing member; the old owner becomes an admin. `owner` can't be given through the member routes (`400`), and the owner can't be removed or have their role changed (`409`).
- Only the owner grants or takes away `admin`, so admins can't promote each other.
- Anyone except the owner can leave (`DELETE /workspaces/:id/members/<their own id>`).
- People holding the global `admin:users` permission (and the admin API key) act as owner in every workspace, and see every workspace in `GET /workspaces`.
- Someone who isn't a member gets `404` for the workspace and everything under it, so workspace ids can't be probed. A member whose role is too low gets `403`.
- API keys other than the admin key aren't members of anything, so they can't use workspaces.

**Members are existing users.** Adding a member takes an email and looks up the user in `design-system-users`; an unknown or disabled email returns `404` ("Ask an administrator to create their account first"). There are no pending invitations. Emails are compared case-insensitively and a person can only be a member once (`409`).

## Items

Eighteen kinds, all through one API: `fonts`, `assets`, `tokens`, `reviews`, `session-replays`, `journey-maps`, `hcd-reports`, `user-personas`, `research-artifacts`, `insights`, `patterns`, `icons`, `interactives`, `stock-photos`, `illustrations`, `capability-logos`, `style-dictionaries`, `guidelines`. Each kind has its own fields, defined and validated in `backend/src/workspaces/resource-kinds.ts` (the frontend mirrors them in `components/workspaces/resourceKinds.js`). Any other kind returns `404`.

- Ids are generated by the server (`res_` + 24 hex characters). The server sets `workspaceId` (from the path), `kind`, `sharedWith`, `isGlobal`, `createdAt/By` and `updatedAt/By`; sending any of them is a `400`.
- Every route is scoped by the workspace in the path. An item can only be changed, deleted or shared through the workspace that owns it; through any other workspace it is `404`, even for someone who is a member of both.
- Reading a workspace's items returns its own items, items other workspaces shared with it, and global items. Shared and global items are read-only outside their workspace.
- URL fields (`url`, `thumbnailUrl`) must be `http(s)` and at most 2048 characters. The server never fetches them; the browser only shows images and links with http(s) URLs.
- **Markup.** `icons.svg` must look like SVG (at most 100KB) and `guidelines.content` is Markdown with HTML allowed (at most 200KB). The server stores them as given; the browser sanitizes them with DOMPurify before display (`components/workspaces/safeContent.js`): icon SVG is sanitized with the SVG profile and shown as an `<img>` data URI, guideline content is rendered with `marked` and sanitized before `v-html`. Raw markup is never put in the page. Other clients must do the same.
- `style-dictionaries.tokens` and `user-personas.demographics` are JSON objects (at most 512KB and 8KB).

### Sharing

`PUT /workspaces/:id/resources/:kind/:rid/sharing` with `{ workspaceIds: [...], isGlobal? }` replaces who can read the item.

- Needs `editor`. Needs `admin` when the workspace has **Require approval for sharing** on, and always to make an item global or stop it being global.
- With **Allow external sharing** off, nothing can be shared or made global (`403`). Turning the setting off withdraws everything the workspace already shared or made global, items and components.
- A global item is visible everywhere, so sharing it with specific workspaces is a `409` (send `workspaceIds: []`).
- Every workspace id must exist (`400`), and the item's own workspace can't be in the list.
- Components that belong to the workspace are shared the same way with `PUT /workspaces/:id/components/:componentId/sharing`.

## Applications

An application belongs to at most one workspace (`workspaceId`).

- Reading applications needs any signed-in principal.
- Registering, changing and deleting need **`admin:governance`, or the `admin` role in the application's workspace**. Applications without a workspace can only be changed with `admin:governance`. Moving an application to another workspace needs admin in both.
- Ids are generated by the server (`app_` + 24 hex characters). Names are unique within a workspace (`409`).
- `PUT /applications/:id` changes only `name`, `description`, `repository`, `version`, `applicationUrl`, `teamId` and `metadata` (replaced as a whole). Capabilities, workspace and design-system version have their own routes; `id`, `registeredAt`, `capabilities`, `workspaceId` and `designSystemVersion` in a `PUT` body are a `400`.
- `repository` and `applicationUrl` must be `http(s)`; they are only displayed.
- Missing applications are `404` on every route.

### Capabilities

- **Governance:** `enabled`, `rules` (rule ids from `GET /governance/rules`; empty means every enabled rule. An application scan without `ruleIds` runs these, skipping any deleted or disabled since) and `scanSchedule`.
- **Visual regression:** enabling it creates a visual-regression project (`argosProjectId` is required; `argosBaseUrl` must be on `ARGOS_ALLOWED_BASE_URLS`; `argosBranch` defaults to `ARGOS_DEFAULT_BRANCH` or `main`). `argosToken` is passed to the project, where it is encrypted, and never stored on or returned with the application.
- **Session replay:** enabling it creates a session-replay project (`openreplayProjectKey` is required). `openreplayApiKey` is handled like `argosToken`. `openreplayBaseUrl` must be a public http(s) address or listed in `OPENREPLAY_ALLOWED_BASE_URLS` (see below).
- If creating a project fails, the request fails with that error and nothing is saved; a project created earlier in the same request is deleted again. Changing an enabled capability's settings updates its project. Disabling a capability keeps the project; deleting the application deletes both projects.
- Linked projects have fixed ids (`vrp_<applicationId>`, `srp_<applicationId>`), so two requests enabling a capability at once share one project, and a request that loses the write race reuses its project on retry. A request that finally fails deletes the project it made unless the stored application links it.
- A linked project that no longer exists is recreated when the capability is enabled again (visual regression needs `argosToken` for that, since the token went with the project; without it the request is a `400` saying so) and unlinked when the capability is disabled.
- The projects belong to the application's workspace (see below) and move with it; `teamId` (or the workspace id) is kept on them as a label.

### Visual regression and session replay projects

Projects and visual-regression runs are stored in Elasticsearch (`design-system-visual-regression-projects`, `design-system-visual-regression-runs`, `design-system-session-replay-projects`); Argos tokens, OpenReplay API keys and webhook secrets are encrypted at rest and never returned. Every project route (`/visual-regression/...`, `/session-replay/...`) and every WebSocket subscription (`subscribe:project`, `subscribe:run`) checks access to the project:

| Project | Read (view, runs, results, sessions, analytics) | Run (trigger runs, approve/reject diffs, baselines) | Manage (change, delete, notifications, webhook secret) |
|---|---|---|---|
| In a workspace | viewer | editor | editor; admin when the project backs an application |
| No workspace | its creator | its creator | its creator |

- `admin:users` holders can do everything with every project; `admin:governance` holders with every application-linked project.
- Callers who can't read a project get `404`; readers without the role get `403`. Lists only show readable projects.
- `POST .../projects` takes an optional `workspaceId` (needs the editor role there). Without one, the project belongs to whoever created it (a user or an API key).
- Not implemented, so they answer `501` instead of pretending: `GET /visual-regression/projects/:id/reports/pdf` (use `.../analytics`), `POST .../baselines/:baselineId/rollback`, and `POST .../share` (share a project by adding people to its workspace).

### Design system versions

`GET /design-system/current-version` returns `{ version, source }`. The version is `DESIGN_SYSTEM_VERSION` when that is set to a semantic version (`source: "DESIGN_SYSTEM_VERSION"`), otherwise the backend's own `package.json` version (`source: "backend-package"`). Set `DESIGN_SYSTEM_VERSION` to the released design system version.

Versions are compared numerically (`2.10.0` is newer than `2.9.0`; pre-release suffixes are ignored). An application without a version counts as needing an upgrade. Breaking changes for a version come from the changelog module's entries marked breaking for that version (`breakingChangesSource: "changelog"`); nothing is invented, so the list is empty until such entries are recorded.

### OpenReplay base URLs (SSRF)

The session-replay service fetches `openreplayBaseUrl`, so it is checked when a project is saved and again before every request to it (DNS can change), in `backend/src/session-replay/openreplay-url.ts`:

- `OPENREPLAY_BASE_URL` (default `https://api.openreplay.com`) and the comma-separated `OPENREPLAY_ALLOWED_BASE_URLS` are trusted, including internal hosts, for self-hosted instances.
- Any other URL must be http(s), without credentials, and resolve only to public addresses (no loopback, private, link-local or metadata ranges). Otherwise `400`.
- Requests don't follow redirects.

## Analytics

`GET /workspaces/:id/analytics` (viewer) is computed from data, with no estimates or random numbers:

- `totalComponents`, `componentsByStatus` and `designDebt` (deprecated components) count the components the workspace can see (its own, shared with it, global).
- `totalApplications` counts its applications.
- Adoption figures (`adoptionRate`, `mostUsedComponents`, `adoptionMetrics.*`) use the component usage recorded by application scans (AnalyticsService) for the workspace's applications. When none has been recorded, `usageDataAvailable` is `false` and those figures are `null` or empty.
- `healthScore` is `100 − 5 × deprecated − 2 × in-progress`, clamped to 0–100, and `null` without components.

`GET /workspaces/analytics/compare?workspaceIds=a,b` compares the workspaces the caller can see. `GET /workspaces` includes a `summary` per workspace (`memberCount`, `applicationCount`, `componentCount`, `healthScore`), so the list page doesn't call analytics per workspace.

## Deleting

- **Workspace** (owner): refused with `409` while applications or components belong to it, with a message saying how many; move or delete them first (`PATCH /applications/:id/workspace`). Otherwise its items are deleted, it is removed from other items' and components' share lists, and the workspace is deleted. Returns `{ deletedItems }`.
- **Application:** deletes its visual-regression and session-replay projects, then the application.

## Routes

All under `/api/v1`. "Role" is the per-workspace role needed.

### Workspaces

| Method and path | Role | Body | Returns |
| --- | --- | --- | --- |
| `GET /workspaces` | member (all for `admin:users`; `?mine=true` for only theirs) | | `Workspace[]` with `summary` |
| `POST /workspaces` | any signed-in user | `{ name, description?, slug?, settings?, metadata?, ownerEmail? }` | `Workspace`. `ownerEmail` is for `admin:users` holders (required for API keys). The slug is derived from the name with a `-2`, `-3`… suffix if taken; a given slug that is taken is a `409`. |
| `GET /workspaces/slug/:slug` | viewer | | `Workspace` |
| `GET /workspaces/:id` | viewer | | `Workspace` |
| `PATCH /workspaces/:id` (also `PUT`) | admin | `{ name?, description?, slug?, settings?, metadata? }` | `Workspace` |
| `DELETE /workspaces/:id` | owner | | `{ deletedItems }`, or `409` |
| `POST /workspaces/:id/members` | admin (owner for `admin`) | `{ email, role }` | `Workspace` |
| `PATCH /workspaces/:id/members/:userId` (also `…/role`) | admin (owner for `admin`) | `{ role }` | `Workspace` |
| `DELETE /workspaces/:id/members/:userId` | admin (owner for admins; anyone for themself) | | `Workspace`, or `{ left: true }` |
| `POST /workspaces/:id/transfer-ownership` | owner | `{ userId }` | `Workspace` |
| `GET /workspaces/:id/components?status=` | viewer | | `{ components, count }` |
| `PUT /workspaces/:id/components/:componentId/sharing` | editor (see Sharing) | `{ workspaceIds, isGlobal? }` | the component |
| `GET /workspaces/:id/analytics` | viewer | | see Analytics |
| `GET /workspaces/analytics/compare?workspaceIds=` | any | | rows for visible workspaces |

`Workspace` is `{ id, name, description, slug, ownerId, members: [{ userId, email, name, role, addedAt, addedBy: { id, name } }], settings: { allowExternalSharing, requireApprovalForSharing, defaultComponentStatus }, metadata, createdAt, updatedAt, createdBy, myRole, effectiveRole }`. `myRole` is the caller's membership role (null when they aren't a member); `effectiveRole` is what they can do.

### Items

| Method and path | Role | Body |
| --- | --- | --- |
| `GET /workspaces/:id/resources/:kind?filter=` | viewer | |
| `POST /workspaces/:id/resources/:kind` | editor | the kind's fields |
| `GET /workspaces/:id/resources/:kind/:rid` | viewer | |
| `PATCH /workspaces/:id/resources/:kind/:rid` | editor | some of the kind's fields (none may be `null`) |
| `DELETE /workspaces/:id/resources/:kind/:rid` | editor | `204` |
| `PUT /workspaces/:id/resources/:kind/:rid/sharing` | editor or admin (see Sharing) | `{ workspaceIds, isGlobal? }` |
| `POST /workspaces/:id/style-dictionaries` | editor | kept for the Design Extractor page; same as `POST …/resources/style-dictionaries` |

An item is `{ ...kind fields, id, kind, workspaceId, sharedWith, isGlobal, createdAt, updatedAt, createdBy, updatedBy }`. `filter` matches the kind's main category field (for example `type` for assets, `category` for tokens).

### Per user

For the user management page:

| Method and path | Permission | Body | Returns |
| --- | --- | --- | --- |
| `GET /users/:userId/workspaces` | `admin:users`, or the user themself | | `[{ workspaceId, name, slug, role }]` |
| `POST /users/:userId/workspaces` | admin of the workspace (owner for `admin`) | `{ workspaceId, role }` | `Workspace` |
| `DELETE /users/:userId/workspaces/:workspaceId` | as `DELETE /workspaces/:id/members/:userId` | | `Workspace` or `{ left: true }` |

### Applications

| Method and path | Permission | Body or returns |
| --- | --- | --- |
| `GET /applications?teamId=&workspaceId=&capability=` | any | `{ applications, count }` |
| `POST /applications/register` | `admin:governance`, or admin of `workspaceId` | `{ name, workspaceId?, description?, repository?, version?, designSystemVersion?, applicationUrl?, teamId?, metadata?, capabilities? }` |
| `GET /applications/version-tracking` | any | `{ currentVersion, currentVersionSource, applicationsByVersion, upgradeSummary, recommendedActions }` |
| `GET /applications/needing-upgrade?currentVersion=` | any | `{ applications, currentVersion, upgradeRequired }` |
| `GET /applications/affected-by-breaking-changes?version=` | any | `{ applications, affectedCount, breakingChanges, breakingChangesSource }`; `version` is required |
| `GET /applications/:id` | any | `Application` |
| `PUT /applications/:id` | write (see above) | editable fields |
| `PATCH /applications/:id/capabilities` | write | `{ governance?, visualRegression?, sessionReplay? }` |
| `PATCH /applications/:id/design-system-version` | write | `{ version }` (semantic version) |
| `PATCH /applications/:id/workspace` | write in both workspaces | `{ workspaceId }` (`null` needs `admin:governance`) |
| `DELETE /applications/:id` | write | `{ success: true }` |
| `GET /design-system/current-version` | any | `{ version, source }` |

The literal `applications/...` routes are declared before `applications/:id`, so the parameter route doesn't capture them.

## Storage

| Index | Holds |
| --- | --- |
| `design-system-workspaces` | Workspaces, with members embedded and a `memberIds` keyword array for "my workspaces" queries |
| `design-system-workspace-resources` | Items of every kind; `kind`, `workspaceId`, `sharedWith` and `isGlobal` are mapped, the kind's fields are kept in `fields` |
| `design-system-applications` | Applications |

Indices are created with `dynamic: false`. Writes use optimistic concurrency (sequence number and primary term) and retry on a conflict; two workspace creates racing for the same slug are resolved by keeping the earlier one. If Elasticsearch is down, reads and writes return `503`.

**Migration:** workspaces, items and applications used to live in memory, so there is nothing to migrate: they were lost on every restart. The sample applications (`app-1`, `app-2`, `app-3`) are no longer created. Re-register applications and recreate workspaces after upgrading.

## Relation to review teams

The reviews module has its own **teams** (`/teams`, index `reviews-teams`, members by email with review roles). They are separate from workspaces: a review team decides who can see and approve design reviews, a workspace groups a team's design system work. They are not linked today; a review's `teamId` is a review team, and a workspace's `reviews` items are links to reviews, not the reviews themselves. Merging the two models is future work.

## Frontend

- `WorkspaceManagement.vue` lists workspaces with their summaries; members and settings open in a dialog. Buttons are shown by `effectiveRole`; the server enforces.
- `WorkspaceDetail.vue` has Overview, Items, Members, Analytics and Settings tabs. The tab and item kind are in the query string, and the page reloads when the workspace id in the route changes. Items load one kind at a time through `useWorkspaceResource(workspaceId, kind)` and `WorkspaceResourceList.vue`.
- `ApplicationManagement.vue` edits details, capabilities and workspace in one dialog and keeps the stored Argos branch and base URL. `ApplicationRegistration.vue` lists the workspaces the user administers.
- Errors are shown inline (`useNotice` + `InlineNotice`); confirmations use `ConfirmDialog` (`useConfirmDialog`), not `window.confirm`. Nothing falls back to sample data when a request fails.
- The router allows `/admin/workspaces` only to `admin:users` holders (see AUTH.md); workspace members without that permission can use the API but not these pages until that guard changes.
